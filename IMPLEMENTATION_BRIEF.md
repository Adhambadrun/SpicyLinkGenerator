# Spicy Link Generator — evidence-first airline handoff brief

This is the executable brief for the next coding session, based on the conversation. Work in **this repository**, not the imagined `lib/airlines/*` implementation described in earlier chat. Never assert that a guessed URL opens a payment page or that a fabricated fare is live.

## Goal and hard boundaries

Given a GDS itinerary or an actual Matrix-style itinerary JSON, expose *airline-direct* options with clear provenance and measured landing-page behavior. Preserve original JSON when imported. Never send passenger names, passport numbers, or payment information in a query string. A search prefill is **not** a cart or checkout link. Do not infer an airline website's checkout behavior from its PSS vendor; websites can and do implement their own handoffs. No single universal airline connector exists.

## Existing implementation (as of this brief)

- `app.html` parses some Sabre/Amadeus-like text locally and exports an illustrative Matrix-shaped JSON. For raw GDS text it **invents** fare basis, fare construction, taxes, and price. Those fields are not suitable for ticketing or live fare validation.
- `booking-tools.js` now imports `itinerary.slices[].segments[]` JSON with strict per-segment checks. On copy, it preserves the original imported object rather than replacing its fare fields with estimates. Unsupported JSON fails without dropping legs.
- `airline-directory.js` provides candidate homepage fallbacks for common marketing carriers; unknown carriers get no link. Its entries have **not** been live checked. When AA is selected, Generate copies and opens the original historical metasearch URL, and Copy copies the same URL; the payload retains every itinerary leg, including mixed-carrier trips, without verifying that AA can pin non-AA-marketed flights. Delta/United search-prefills remain unverified for eligible direct itineraries. Other mixed-carrier selections fall back to the selected airline homepage. The app has a logo-bearing airline selector beside Generate/Copy. Fabricated Delta cart/price URLs were removed. See `AA_ACCEPTANCE.md` for the live fare-match gate.
- Existing AA/Delta experimental links are not evidenced as active airline carts. They must not be sold as a direct-payment or passenger-prefill feature. No Google Flights scraping, live fare provider, passenger-data handoff, or airline API integration has been added.

## Next phases: implement only with verifiable evidence

1. **Fixture-driven parser**: Collect non-sensitive, permitted test fixtures from actual GDS and Matrix exports. Test multi-city, married segments, marketing vs operating carrier, year boundaries, timezone and passenger-type handling. Parse fare basis only if present; never synthesize one for an actual booking quote. No unparsed leg may be silently ignored. Validate any claim of BookWithMatrix compatibility with a documented fixture and actual acceptance test; shaped JSON alone is not proof.
2. **Connector registry**: Per *airline website*, record official domain, documented URL/API specification, evidence source/date, exact input fields, target step (`homepage`, `search`, `selection`, `passenger`, `payment`), auth/partner requirements, last human test date and fallback. Registry entries without evidence must say `unverified` and return a safe search/homepage option, not a fake checkout session. Only implement specific e-Retail, Sabre, Navitaire or custom formats after validation against that particular airline; no universal `Override.action`, `AirBook` token encryption, `/v5/booking/create`, JWT signer, or generic NDC `CheckoutURL` recipe.
3. **Live fare verification**: An authorized provider adapter must search/reprice *the complete itinerary together* (including passenger mix, point of sale, cabin and fare basis when supported). Distinguish `not_checked`, `unavailable`, `changed`, `verified_as_of`, `error`; report observed price/currency, provider ID and server timestamp. Never treat elapsed time, booking class, or demand multipliers as proof of seat availability. Expose APIs behind the existing session check, validate input, bound payload and timeout, rate-limit, and keep credentials server-side. Do not log PII or tokens.
4. **Airline handoff**: If a contracted API actually returns a redirect URL, use *that exact URL* after validating HTTPS and the airline-domain allowlist and report the offer/session expiration furnished by the provider. Creating an NDC order is not the same as receiving a consumer checkout URL; never create a PNR/order in an informational click-out without explicit user consent and supported workflow. If no authorized handoff exists, show search prefill with a clear warning that flight/fare/passengers may need re-selection. Require consent before transmitting optional passenger details. Never auto-submit arbitrary HTML forms.
5. **Google Flights research**: With a human-controlled browser session, document observable click-out behavior and the final landing page of an airline-direct option, redacting all cookies, personal data and tokens. Google `batchexecute` payload indices, token contents, crypto algorithms, backend partner calls, and redirect paths in the prior chat were **speculative**, not verified specifications. Do not implement credential/cookie harvesting, anti-bot evasion, CAPTCHA solving, residential proxy rotation or token replay. An observed Google redirect is not a reusable affiliate API or a universal booking session.
6. **Coverage testing**: Automated parser/schema tests; mocked provider integration tests for reprice, unavailable, stale, error, and timeouts; domain-allowlist/open-redirect tests; manual airline-by-airline smoke tests (real browser, no payment). Record results with dates, screenshots redacting PII, and fallback destinations. Unsupported carriers must be reported as unsupported rather than padded into a coverage count.

## Acceptance criteria

- A user can distinguish **original imported fare**, **illustrative synthetic estimate**, **live repriced offer**, and **unknown** at a glance.
- A user can distinguish **search** from **passenger** from **payment**, with verified per-airline evidence; unsupported or stale claims fall back to search or no link.
- Every nontrivial itinerary retains all legs or returns a clear failure; no fabricated fare, token or price is described as real.
- `npm test` passes, secrets remain off the client, and the existing sign-in behavior is not weakened.

## Security debt to review before production expansion

The current public-repository default `AUTH_SECRET` permits forged sessions if not overridden in deployment. Stateless OTP verification also cannot guarantee one-time use or a global five-attempt limit when old signed challenge tokens are reused. A cookie is shared among tabs; `sessionStorage` is a UI gate, not a server-enforced per-tab session. Fix these separately before exposing provider credentials or passenger PII to this application.
